# 综合办公 Agent：产品概要

> 状态：方向草案 v0.3。当前以 Python、LangChain 和 LangGraph 作为学习与 MVP 原型技术主线；Hermes 作为参考实现。首个验证场景为制造业客户访谈整理与跟进；用户痛点、任务频率、产品价值和部署形态仍待验证。

## 一句话

帮助团队处理跨应用的日常办公任务，把分散的信息转成可检查、可编辑、可交付的工作成果。首个验证切口聚焦制造业数字化转型/出海服务项目的客户访谈整理与跟进。

## 问题与机会

办公任务常常跨越消息、会议、文档、表格、日历和任务系统。人需要在多个应用间搬运上下文、整理信息、起草内容并跟进后续动作。Agent 可以协助理解上下文和生成成果，但只有在结果可核查、数据使用清楚、外部操作受控时，才适合进入真实工作流程。

这是产品机会假设，不代表已经验证了具体用户、最高频任务或付费意愿。

## 当前用户与场景假设

- **首批用户假设：** 为制造业客户提供数字化转型、出海或相关咨询服务的项目/交付人员。
- **核心任务假设：** 客户访谈后，从转写或笔记整理客户现状、需求、问题、待确认事项和下一步，并准备跟进邮件草稿。
- **审核者：** 负责项目推进或客户沟通的人员，对事实、判断和后续承诺负责。
- **未验证事项：** 这类任务的发生频率、现有耗时、错误代价、可用材料以及用户是否愿意改变现有流程。

这一选择用于获得具体反馈，不代表已证明市场需求。优先从用户有权提供的少量真实或脱敏访谈材料验证。不要仅因为某个 Agent 框架支持某个渠道或工具，就把它自动列入目标用户需求。

## 产品目标

先验证 Agent 能否把一次客户访谈材料整理成可追溯、可编辑的团队跟进简报，并减少人工整理时间，同时由项目人员掌握客户沟通和外部写入决定。更广泛的跨应用办公能力是长期方向，不是首版承诺。

## 产品原则

1. **先完成一条真实工作流。** 以用户任务的输入、处理中间状态和最终成果定义范围，不以集成应用数量定义进展。
2. **草稿和行动分开。** 生成文档、邮件或任务草稿不等于用户批准发送、创建或更新。
3. **上下文有出处。** 展示 Agent 使用了哪些用户输入、文件或连接器信息；无法确认的内容明确标示。
4. **外部写入需可控。** 发送消息、创建或修改办公记录等动作，首版默认先预览并由用户确认；授权范围必须清楚。
5. **数据按用户/工作区隔离。** 连接器权限、模型服务的数据路径、保存期限和日志策略需在接入真实资料前确认。
6. **失败可恢复。** 任务失败时保留输入和已有结果，说明失败阶段并提供继续、重试或导出能力。

## 不在当前承诺范围内

- 一开始覆盖所有办公应用和全部职能。
- 无人审核地发送邮件、发布内容或修改关键业务数据。
- 假设所有场景都可以把完整工作区资料发送给任意模型服务。
- 因为底座支持多 Agent、定时任务或大量集成，就在首版同时引入这些能力。

## 待验证问题

1. 客户访谈整理是否足够频繁、耗时，值得成为首个场景？
2. 项目人员对简报结构、事实溯源和跟进邮件草稿是否认可？
3. 哪种输入格式最常见，首版用粘贴文本还是上传文件即可验证？
4. 样本材料有哪些保密要求，允许使用的模型和存储方式是什么？
5. 用户是否需要把确认后的行动写入某个办公系统，还是导出文本已足够？
6. 选定的 Python 框架和模型服务，其运行模式、工具接口和数据行为是否满足原型与隐私要求？

## 成功信号

按照 [`MVP_WORKFLOW.md`](MVP_WORKFLOW.md) 建立人工基线，再用少量真实任务观察：

- 完成任务的总时间和用户实际节省的步骤；
- 输出需要修改的比例及错误类型；
- 用户能否理解依据并发现不确定项；
- 需要外部写入时，用户是否能正确预览和确认；
- 用户是否愿意把同类任务再次交给产品。

样本较少时，结果仅用于发现问题，不用于宣称普遍效果。
