# 综合办公 Agent：产品概要

> 状态：方向草案 v0.5。当前以 Python、LangChain 和 LangGraph 作为学习与 MVP 原型技术主线；Hermes 作为参考实现。用户已选定制造业售后工单处理 Agent 作为首个验证场景，并已确认产品形态（CLI + 自有图形界面）；真实团队痛点、工单频率、产品价值和部署环境仍待验证。

## 一句话

帮助团队处理日常办公任务，把分散的信息转成可检查、可编辑、可交付的工作成果。首个验证切口聚焦制造业企业售后支持：根据工单和授权的产品资料，形成可追溯、可审核的处理建议与回复草稿。

## 问题与机会

制造业售后人员需要理解客户问题、识别产品型号和故障线索、查阅手册/服务政策、决定是否升级，并撰写客户回复。资料分散或处理口径不一致会延长响应时间，也可能造成错误承诺。Agent 可以协助整理工单和检索依据，但建议必须可核查，安全和保修边界必须明确。

这是产品机会假设，不代表已经验证了具体用户、最高频任务或付费意愿。

## 当前用户与场景假设

- **首批用户假设：** 制造业企业的售后支持/技术服务人员，以及审核复杂工单的资深工程师或服务主管。
- **核心任务假设：** 根据一条售后工单和授权的产品资料，完成问题分类、依据查找、待补信息整理、升级判断和回复草稿。
- **审核者：** 对维修建议、保修口径和客户承诺负责的售后工程师或主管。
- **未验证事项：** 工单量和重复度、人工首响耗时、知识资料质量、错误代价，以及团队是否愿意把工单交给 Agent 辅助处理。

这一选择是用户选定的验证方向，不代表市场需求已证明。优先从用户有权提供的少量真实或脱敏工单及对应产品资料开始。不要仅因为某个 Agent 框架支持某个渠道或工具，就把它自动列入产品需求。

## 产品目标

先验证 Agent 能否帮助售后人员更快地理解工单、找到经批准资料中的依据、准备回复草稿并正确识别需要升级的情况。人仍负责审核维修建议和对客户的承诺。更广泛的跨应用办公能力是长期方向，不是首版承诺。

## 产品形态（已确认，2026-11-01）

用户已确认产品要同时提供两种使用方式：

- **终端 CLI：** 输入 `ya` 即可启动 Agent，交互方式参照 Hermes CLI，面向开发者和熟悉终端的用户。
- **自有图形界面：** 面向非开发者用户（如售后支持人员），同一套能力，无需终端操作。

两者共用**同一个 Python 核心**，不各自实现业务逻辑；界面只负责呈现、输入和审核交互。分层设计、前端技术选型（React + Electron 桌面壳）、分阶段关卡与重新评估条件见[决策 0004](decisions/0004-cli-and-desktop-entry-architecture.md)。

需要区分的边界：**形态确认不等于需求验证。** 工具能被装到用户机器上，不代表售后团队真的需要它或愿意用；首版图形界面仍是审核面板，用于核对依据和修改草稿，不承担自动发送或写入外部系统。

## 产品原则

1. **先完成一条真实工作流。** 以用户任务的输入、处理中间状态和最终成果定义范围，不以集成应用数量定义进展。
2. **草稿和行动分开。** 生成文档、邮件或任务草稿不等于用户批准发送、创建或更新。
3. **上下文有出处。** 展示 Agent 使用了哪些用户输入、文件或连接器信息；无法确认的内容明确标示。
4. **外部写入需可控。** 发送消息、创建或修改办公记录等动作，首版默认先预览并由用户确认；授权范围必须清楚。
5. **数据按用户/工作区隔离。** 连接器权限、模型服务的数据路径、保存期限和日志策略需在接入真实资料前确认。
6. **失败可恢复。** 任务失败时保留输入和已有结果，说明失败阶段并提供继续、重试或导出能力。
7. **安全边界清楚。** 证据不足、涉及设备/人身安全或服务政策冲突时，明确升级给人工，不猜测操作步骤。

## 不在当前承诺范围内

- 一开始覆盖所有办公应用和全部职能。
- 无人审核地发送邮件、发布内容或修改关键业务数据。
- 假设所有场景都可以把完整工作区资料发送给任意模型服务。
- 因为底座支持多 Agent、定时任务或大量集成，就在首版同时引入这些能力。

## 待验证问题

1. 售后团队是否有足够高频、重复且可审核的服务工单？
2. 处理工单需要哪些资料：产品手册、维修 SOP、保修政策、历史案例还是其他？
3. 哪些故障类型必须转给人工，哪些只能提供非操作性信息？
4. 售后人员认为哪些输出有用：分类、证据摘录、补充问题、升级建议或回复草稿？
5. 哪些获准使用的脱敏工单可用于首轮验证，数据能否发送给选定模型服务？
6. 首版手动导入/导出是否足够，还是存在必须集成的工单系统？
7. 选定的 Python 框架和模型服务，其运行模式、工具接口和数据行为是否满足原型与隐私要求？

## 成功信号

按照 [`MVP_WORKFLOW.md`](MVP_WORKFLOW.md) 建立人工基线，再用少量工单样本观察：

- 完成任务的总时间和用户实际节省的步骤；
- 输出需要修改的比例及错误类型；
- 用户能否理解依据并发现不确定项；
- 涉及安全风险、保修例外或资料冲突时，是否能正确升级给人工；
- 售后人员是否愿意在下一条类似工单继续使用。

样本较少时，结果仅用于发现问题，不用于宣称普遍效果。
