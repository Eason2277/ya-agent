# 决策 0003：以制造业售后工单处理 Agent 作为首个产品切片

- 日期：2026-10-29
- 状态：用户已选择该方向；仍是待验证的 MVP 假设
- 替代范围：取代决策 0001 中“制造业客户访谈整理与跟进”作为首个产品场景的选择；不改变决策 0002 的 Python、LangChain、LangGraph 学习与原型技术路线。

## 背景

产品长期方向仍是综合办公 Agent，但该范围太宽，尚不能指导首版实现。此前曾选择客户访谈整理作为候选工作流；用户随后决定改为制造业售后服务场景。

用户当前选择的切片是：帮助制造业企业售后支持人员处理产品服务工单，结合授权的产品手册、服务政策和历史案例，生成可追溯的分析与回复草稿。这个选择是明确的项目方向，但售后团队的实际痛点、数据可得性和产品价值仍未通过试用验证。

## 决定

- **目标用户假设：** 制造业企业的售后支持/技术服务人员，以及负责审核复杂工单的资深工程师或主管。
- **主要输入：** 用户选择的一条售后工单，以及本次任务明确授权使用的产品资料。
- **主要输出：** 问题摘要和类别、来源依据、待补信息、建议下一步、升级人工标记及回复草稿。
- **人工边界：** 首版只提供建议与草稿；用户确认前不发送回复、不更新工单系统、不下发维修指令，也不远程操作设备。
- **第一验证方法：** 用少量获准使用或脱敏的工单与对应手册/政策，对比人工基线、依据准确性、修改情况和售后人员复用意愿。

## 选择理由

- 工单、产品型号、手册和服务政策提供了较清晰的输入、知识来源与可审核输出，适合作为狭窄的 Agent 工作流练习。
- 分类、检索、证据引用、缺失信息追问和人工升级都能分步实现，方便学习 Python、Pydantic 与后续 LangChain/LangGraph。
- 首版不执行外部写入或设备操作，可以先验证信息整理和草稿价值，降低错误后果。

以上理由说明该切片便于验证，不证明目标团队已经有足够需求或愿意采用。

## 风险与边界

- 错误维修建议可能造成设备损坏或人身安全风险；安全相关和证据不足的工单必须升级给人工，不能生成无依据的操作步骤。
- 错误保修判断、费用、交付时间或处理承诺可能产生业务损失；此类信息必须引用正式政策并由人员审核。
- 企业工单和产品资料可能含客户机密或个人信息。使用前确认授权、脱敏、模型服务数据路径、保存和日志策略。
- 若没有稳定的资料来源或无法找到愿意参与验证的售后团队，先不要做复杂连接器；重新评估场景或暂停。
- 如果人工审核后仍频繁更正核心分类/建议，或证据引用无法可靠核验，应收窄为工单整理/分流，而不是增加自动执行权限。

## 下一步

选一条虚构或获准脱敏的工单和一段对应产品资料，先确定最小输入与输出字段；再由用户一步一步修改 `schemas.py`，之后才接模型调用。
