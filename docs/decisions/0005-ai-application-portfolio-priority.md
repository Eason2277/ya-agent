# 决策 0005：面向 AI 应用全栈岗位建设可验证作品

- 日期：2026-11-08
- 状态：已决定实施顺序；用户确认求职目标为 AI 应用岗位，并在 2026-11-08 进一步明确要掌握完整 AI 应用全栈研发。售后场景的客户价值仍是待验证假设。
- 关系：补充决策 0002 的学习主线、0003 的售后场景和 0004 的入口分层；不撤销用户确认的 `ya` CLI 与图形界面形态。
- 依据：[官方招聘岗位小样本与 Ya Agent 取舍](../research/2026-11-08-ai-application-jobs.md)。样本有选择偏差，不能推出市场份额、录用率或统一技术栈。

## 背景

用户明确希望从前端经验走向完整的 AI 应用全栈研发，同时要求产品和技术调整符合可核对事实。当前原型有模型调用、结构化结果和逐字引文检查，但没有可供售后人员审核的完整应用。岗位样本更强调业务流程、后端/API、资料或工具接入、评测、稳定性和实际交付；平台/算法岗位的多 Agent、海量并发和模型训练要求不等于应用岗的首版要求。

## 决定

1. **产品切片继续用制造业售后工单。** 它是用户已选择、能够把输入资料、处理建议和人工审核连成一条线的工程验证场景；招聘页面不能证明售后团队确有需求。能否取得获准样本、是否节省人工审核时间，仍按 `MVP_WORKFLOW.md` 验证。
2. **作品目标定为可演示、可解释的 AI 应用全栈闭环。** 一条工单能输入、选择资料、生成结构化建议、看到来源和未知项、修改草稿、处理失败并导出；开发者还要能解释 React 界面、FastAPI 接口、Python 核心、数据保存、模型调用与评测各层的输入输出和失败边界。评价时分别展示程序检查和人工复核。已完成的局部能力不得说成完整应用或真实客户交付。
3. **保留 Python 核心和 LangChain 当前用法。** Pydantic 继续定义输入输出。LangGraph 只在需要跨步骤状态、人工暂停/恢复时加入；产品内的 RAG、只读工具和数据库各自以资料遗漏、实际查询、保存审核记录等具体问题为条件。DeepSeek 是当前模型服务，不是产品与岗位的绑定条件。
4. **调整交付优先级。** 完成最小可复现评估和一条薄 `ya` CLI 流程后，优先用 FastAPI + 浏览器审核页面展示完整应用。CLI 的丰富终端交互、Electron 壳与打包仍保留在后续阶段；不因个别岗位提到它们就提前实现。桌面形态是否适合售后团队，要结合目标用户环境和数据路径再验证。
5. **招聘证据定期重查。** 只把岗位小样本用来判断作品展示方向；针对实际投递的岗位、城市和级别另做筛选，避免将“可展示能力”误写为“满足任职条件”。
6. **为应用岗位保留独立学习实验。** 完成首条可审核应用流程后，可以用明确标注为虚构的多资料样本，比较人工选材、简单搜索与 RAG 的命中/答案质量；也可用只读资料查询实验工具调用及越权拒绝。实验应有固定输入、基线、预期和实际结果，放在作品证据中，不自动扩大售后 MVP 的产品承诺。
7. **后端与交付由开发者完整承担。** 浏览器审核流程跑通后，围绕“编辑内容在刷新后仍可恢复”和“失败输入与结果可追踪”设计持久化与数据模型；PostgreSQL 是学习和服务端原型候选，若将来本地桌面分发使其成本过高，再比较 SQLite 等方案。随后以实际应用为对象完成接口验证、必要的权限边界、运行记录和可复现部署。每项都以可运行行为和解释能力验收，不以依赖列表验收。

## 理由与代价

- 这个顺序从用户已有的前端经验出发，让用户亲自完成 Python、后端、数据和 AI 应用工程的端到端实现，同时先形成可操作的产品流程。代价是暂时不能在作品中声称已有 LangGraph、RAG、MCP 或 Electron 实战。
- 维持售后场景可保留现有代码和评估卡，避免因招聘关键词频繁换题；代价是其市场价值未知，必须通过获准资料和售后人员试用来证伪。
- 浏览器审核页面比先做桌面打包更早暴露数据流、审核状态和错误恢复的问题；Electron 仍是已确认的目标形态，但包装成本只在应用闭环可用后承担。

## 重新评估条件

- 若获准售后资料或愿意试用的目标用户长期不可得，或人工审核后仍无可观察的时间/质量改善，重新评估制造业售后场景，而非继续堆技术。
- 若资料规模导致人工选材反复漏依据，先建立应命中资料样本，再比较简单搜索与 RAG。
- 若人工审核必须跨会话暂停/恢复，再设计状态持久化并评估 LangGraph；若单次请求足够，继续用清晰的 Python 流程。
- 若目标应用岗位样本明显转向不同交付环境，或真实售后团队要求内网 Web/本地桌面部署，重新评估 UI、服务和打包方案，并记录实际约束。
