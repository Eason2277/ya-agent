# 决策 0001：以 Nous Research Hermes Agent 为 Agent 基础

- 日期：2026-10-27
- 状态：技术底座选择已被决策 0002 取代；原客户访谈场景已被决策 0003 取代（保留为历史记录）
- 当前本地上游快照：`hermes-agent/` 的 `main`，commit `11a75355a4c5540154597c7ea23cbc2a933539f5`（浅克隆；核对日期：2026-10-27）

## 背景

当时用户计划基于 Nous Research 开源的 Hermes Agent 开发综合办公 Agent，并曾选定制造业数字化转型/出海服务项目中的客户访谈整理与跟进作为第一条 MVP 候选工作流。该场景后来由决策 0003 取代；本文件仅记录当时的产品与技术思路。

## 当时的决定（历史记录）

- Hermes Agent 作为 Agent 能力的上游基础。
- 自有产品负责办公场景、用户体验、连接器授权、项目/工作区上下文、审核流程和产品特有的数据策略。
- 优先通过 Hermes 已支持的配置、工具和扩展边界集成；只有验证出缺口后，才考虑维护上游补丁或修改核心代码。
- 首版按一条用户工作流交付，不因 Hermes 支持多种运行渠道或工具就同时接入。
- 当时拟先用用户选择或提供的访谈材料生成可编辑简报和跟进邮件草稿；该工作流已不再是当前 MVP。

## 理由

- 复用成熟 Agent 基础可以把精力放在用户任务、连接器和可审核成果上。
- 将产品层与 Agent 底座分开，能减少不必要的上游分叉，并让后续升级边界更清楚。
- 综合办公涵盖多种应用和风险级别，需要先通过真实工作流确定哪些底座能力有实际价值。
- 客户访谈当时被认为是一个输入输出可限定、可由项目人员依据原始材料审核的起点；该判断并不代表市场需求已验证。

## 必须验证

在实现真实连接器或处理工作区资料前，检查所用 Hermes 版本及其官方源码/文档，确认：

- 许可证、再分发和商用条件；
- SDK/扩展接口、工具调用和事件生命周期；
- 会话、记忆、文件和凭证的存储位置及隔离方式；
- 模型与工具请求的数据流、日志和遥测行为；
- 权限确认机制、危险操作保护、沙箱能力和失败恢复；
- 支持的操作系统、运行方式、更新策略和资源要求。

此决策记录产品方向，不代表上述技术、安全或法律项已经通过审查。

## 风险与重新评估条件

- Hermes 的接口或许可条件不适合目标产品时，重新比较集成、维护分支或更换底座的成本。
- 如果必要的办公连接器需要广泛权限，先缩小工作流或改为用户选择文件/内容的只读输入。
- 如果升级上游时必须长期维护大量核心补丁，评估是否把产品能力移到独立扩展/连接器层。
- 若部署环境、数据驻留或团队协作需求与 Hermes 当前运行模型冲突，先验证最小端到端切片，再决定是否增加服务端架构。
