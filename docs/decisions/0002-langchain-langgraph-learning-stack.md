# 决策 0002：以 Python、LangChain 和 LangGraph 作为学习与 MVP 原型主线

- 日期：2026-10-27
- 状态：已确认，用于学习和首版原型；不代表产品需求或市场价值已验证
- 取代范围：决策 0001 中“以 Hermes 作为当前产品运行时/Agent 底座”的技术选择。当前产品场景由决策 0003 记录。

## 背景

用户希望在开发综合办公 Agent 的同时补强 Python，并学习中国大陆招聘中常见、可迁移的 Agent 工程技术。Hermes 是功能较完整的开源 Agent 应用，适合阅读成熟实现，但直接从大型应用源码入手不利于循序掌握 Agent 工作流，也不会自然带来 LangChain/LangGraph 的框架经验。

当前 MVP 场景由决策 0003 定义为制造业售后工单处理。此技术栈决策仍然有效；客户访谈整理是此前的历史候选场景。

## 决定

- **主要语言：** Python。
- **入门 Agent API：** 从 LangChain 的高层 Agent API 开始，学习模型调用、工具、结构化输出和基本 Agent 循环。
- **工作流编排：** 当流程需要明确状态、条件分支、人工审核、中断/恢复或长任务管理时，用 LangGraph 表达工作流。售后工单流程可按需组织为：工单理解 → 产品资料检索 → 依据与安全边界核对 → 人工审核 → 回复草稿导出。
- **服务层：** 需要提供前后端接口时用 FastAPI；在接口和任务生命周期尚未明确前，不预先搭建复杂服务架构。
- **Hermes：** 仅通过官方 GitHub 源码和架构文档在线学习，不在 Ya Agent 项目目录保留上游克隆，也不作为当前原型依赖；只有后续评估证明其运行时或扩展机制能显著降低产品成本时，才重新决定是否集成。
- **框架使用原则：** 先理解并实现一个最小流程，不为展示技术栈而强行引入图、多 Agent、向量库或记忆系统。

## Hermes 官方架构对照（2026-11-01）

上游 [GitHub 仓库](https://github.com/NousResearch/hermes-agent) 的 `main` 在核对时指向 `40804ce4074c561220c4a766e116e07b4873b1c3`。以下是从上游 [README](https://github.com/NousResearch/hermes-agent) 和[官方架构说明](https://hermes-agent.nousresearch.com/docs/developer-guide/architecture)整理的高层结构；架构网页会更新，引用具体实现时应再核对相应 commit 的源码。

| Hermes 的层次 | 官方资料描述 | 对 Ya Agent 的启发与当前取舍 |
| --- | --- | --- |
| 入口 | CLI、消息网关、API 等入口汇入 Agent 核心 | 让工单处理逻辑独立于入口；当前先用命令行样本，需要前后端接口时再加 FastAPI。 |
| Agent 循环 | `AIAgent` 组织提示词、模型提供商解析和工具调用；收到工具调用后继续循环 | 当前用 LangChain 接入 DeepSeek 并生成结构化结果；真实任务需要工具或多步状态时再扩展，不复制 Hermes 运行时。 |
| 工具与扩展 | 工具注册与调度、不同执行后端，以及技能、插件和 MCP 接口 | 只为售后工作流增加必要的资料读取与证据核对；不预先接入通用工具集或多平台网关。 |
| 状态与安全 | SQLite/FTS5 会话存储、上下文压缩，以及高风险工具的权限控制 | 当前保留输入、引文和失败边界的设计要求；持久化、权限与人工审核随真实工作流需要逐步实现。 |

这份对照是架构学习材料，不代表 Hermes 的所有能力都是 Ya Agent 的需求，也不改变本决策确定的 Python、LangChain、LangGraph 主线。

## 招聘市场观察（2026-10-27）

对近期可检索到的公开岗位做了小样本抽查：有岗位将 LangChain/LangGraph 与 AutoGen 或自研框架并列为可接受经验，也有岗位重点要求 Python、工具调用、工作流编排、RAG、评估和生产级落地。参考：[美团 Agent 相关岗位](https://zhaopin.meituan.com/web/position/detail?highlightType=social&jobUnionId=4428189649)、[百度 Agent 算法岗位](https://talent.baidu.com/jobs/detail/GRADUATE/4f1cbc80-8332-4a92-b8fa-c0132b17d47e)。

这是公开岗位样本，不是全市场统计，也不能证明某个框架长期占有率最高。选择 LangChain/LangGraph 的理由是它们在样本中可见、Python 生态明确，而且覆盖从高层 Agent API 到状态化编排的学习路径；长期可迁移能力仍是 Python 后端、工具/状态设计、评估、可观测性和可靠性。

**2026-11-08 更新：** 用户已明确求职目标为 AI 应用岗位；新的[招聘方官网岗位小样本](../research/2026-11-08-ai-application-jobs.md)与[决策 0005](0005-ai-application-portfolio-priority.md)补充了岗位类型和作品交付优先级。本节保留 2026-10-27 的历史观察，不能代替新样本或真实投递岗位要求。

LangGraph 官方将自身定位为较底层的状态化编排运行时，并建议 Agent 初学者先从 LangChain 的高层 Agent 开始，再深入 LangGraph：[LangGraph 官方概览](https://docs.langchain.com/oss/python/langgraph/overview)。

## 适用边界

- 当前决策优先服务于学习目标与可验证原型，不宣称 LangChain/LangGraph 是唯一或永久正确的产品架构。
- LangGraph 仅在流程存在显式状态/分支/人工中断需求时使用；简单的一次模型调用或短链路优先保持简单。
- 不在同一个 MVP 中同时维护 Hermes runtime 和 LangGraph runtime。
- 工单分类、处理建议和客户回复均为草稿；首版不自动发送回复、更新工单系统或执行设备操作。
- 接入客户资料前，核实模型服务、日志和存储的数据路径、保留策略与权限；验证样本须获准使用或完成脱敏。

## 风险与重新评估条件

- 框架 API 更新快，开始实现时需以选定版本的官方文档为准，记录依赖版本并验证升级行为。
- 高层抽象可能让调用、状态和失败路径变得不透明；关键模型请求、工具副作用、状态迁移和评估必须能被追踪。
- 如果客户部署要求或 Hermes 的现有渠道/工具能力能显著缩短交付路径，可重新评估 Hermes 集成，但需比较维护、升级、数据隔离和学习成本。
- 如果岗位需求样本或目标团队技术栈发生明显变化，应重新查看近期岗位，而不是长期沿用本记录中的招聘观察。
- 如果首版工作流不需要持久化、中断恢复或人工审核节点，不为“使用 LangGraph”而强行构造图。

## 下一步

先用 Python 完成最窄的售后工单流程：输入一条工单、检索用户提供的少量产品资料、生成带来源的分类和回复草稿；随后再加入人工审核节点，最后判断是否需要完整 LangGraph 状态持久化。每一阶段保留可复现样本和错误记录。
