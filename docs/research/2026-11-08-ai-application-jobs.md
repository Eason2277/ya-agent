# AI 应用开发岗位样本与 Ya Agent 取舍

> 核对日期：2026-11-08（Asia/Shanghai）。目标岗位：在中国大陆招聘的 AI 应用开发、AI 全栈应用和相近的企业智能体交付岗位。资料来自招聘方官网；岗位日期是页面标注的发布或更新日期，不等于岗位仍在招，也不代表全国市场占比。

## 取样方法与限制

- 先检查用户指定的两个美团社招岗位，再从腾讯、百度、京东、华为的官方招聘页面选取与应用交付相近的岗位，并保留若干平台岗位作边界对照。下表是**有目的的小样本**，不是随机抽样；不能用出现次数推断某技术“市场用得最多”、薪资水平或个人录用概率。
- 百度、京东的部分详情页可直接读取正文；美团、腾讯的部分详情页及华为列表在本次工具中动态渲染或返回空正文，因此相应条目依据其**官方域名页面的搜索索引摘录**记录。它们比完整直读页面更可能滞后；实际投递或再次改变技术决策前，应重新打开招聘方页面核对岗位是否仍在招及要求是否变化。
- 把岗位标题、实际职责、工作年限和业务背景一起看。标题含 Agent 的平台、算法、SRE 专家岗位，其要求不能直接当作应用开发岗位的入门清单。
- 字节跳动的官方岗位详情在本次检索中没有可核对的职责正文；阿里巴巴招聘首页可读，但未取得可核对的单个岗位要求。这两家公司未纳入下表，不能把搜索摘要或第三方转载当作其招聘条件。
- 以下“项目启示”是结合 Ya Agent 当前代码和用户选择的应用岗位所作**推断**；岗位要求本身才是来源事实。

## 对岗位要求的归纳

1. **应用岗的重合项：** 几个直接相关岗位都强调把业务流程拆成可交付的 AI 功能、接入模型和资料/工具、设计后端接口、处理失败、评测效果并迭代。这是样本内观察，不是全市场频率结论。
2. **语言和框架没有唯一答案：** 有岗位接受 Python、Java、Go 或 TypeScript；京东的应用岗位以 Java 为基础；腾讯的 Agent 引擎岗位甚至以 TypeScript/Node.js 为主。[百度 Agent 引擎岗位](https://talent.baidu.com/jobs/detail/SOCIAL/d56ce9b0-296b-4615-9497-115968d4fc14)也说明框架名称不能代替后端基础。LangGraph 在样本中出现，但与其他框架并列；FastAPI、Pydantic、DeepSeek 不能被称为招聘市场的统一标准。
3. **应用与平台要分开：** 记忆、多 Agent、沙箱、海量并发、Kubernetes 在若干平台和资深岗位中出现。Ya Agent 的首版工单流没有观察到这些需求；提前加入会增加解释与维护成本，不能自动提升应用岗匹配度。
4. **前端经验有可迁移价值：** 审核界面、来源对照、编辑和失败恢复能展示从模型输出到用户可用任务的完整链路。React 与 Electron 出现在个别相关岗位；样本不支持“Electron 是 AI 应用岗位通用门槛”。
5. **求职效果仍未知：** 岗位页面不是招聘成功率数据。个人工作年限、目标城市、既有项目、面试表现和真实交付经验都会影响结果；一条虚构工单只能证明局部工程行为，不能声称有客户价值或生产经验。

## Ya Agent 的当前证据与缺口

| 能力 | 2026-11-08 可核对状态 | 作品证明力的下一道门槛 |
| --- | --- | --- |
| 模型接入与结构化输出 | `review_ticket.py` 调用 LangChain/DeepSeek 并解析 `TicketReview`；用户用虚构 E18 样本观察到成功和错误引文两条路径。 | 固定输入/预期/结果，能复现解析、引文、无依据承诺等失败分类。 |
| 引文和安全边界 | `evidence.py` 只做逐字包含检查；`tests/test_evidence.py` 的正反两例离线通过。 | 来源名称、结论支持关系、草稿承诺仍需人工审核和更完整的评估记录。 |
| 应用交付 | 示例脚本可运行；`ya` 仍是占位入口，没有 FastAPI、审核页面、编辑/导出或失败恢复界面。 | 完成一条可供人审阅和修改的端到端工单流程，再讨论交付形式。 |
| 真实业务价值 | 尚无获准真实/脱敏工单、人工基线或售后人员试用。 | 获准资料、人工处理基线和小样本反馈；不能用招聘岗位替代需求验证。 |

## 对开发者求职路径的判断（推断）

| 目标岗位 | 当前项目能帮助展示的部分 | 明显缺口或个人条件边界 |
| --- | --- | --- |
| AI 应用全栈开发 | 用户已有前端经验，可亲自把模型结果、证据对照、审核与失败恢复做成完整页面，并实现 Python API、数据流和评测。 | 目前没有 API/页面、持久化、部署与端到端评测；岗位要求的既有工作年限或企业交付经历不能由个人作品替代。 |
| AI 应用后端开发 | 模型接口、结构化结果、数据来源与错误边界是合理起点。 | 还需服务接口、持久化、并发/超时、权限和可观测的实际工程证据；某些岗位另有 Java/Go 经验门槛。 |
| 智能体场景交付/FDE | 明确业务人员任务、获准资料、人工审核与效果评价的过程有迁移价值。 | 真实客户现场、系统联调、部署和业务基线均未验证；用户是否愿意从事现场交付也未知。 |
| Agent 平台/算法岗位 | 当前成果只提供应用层问题和简单回归案例。 | 平台运行时、分布式系统或模型训练经验属于另一条能力路线，不应凭本项目当前形态声称匹配。 |

## 决策建议

- **产品：** 保留制造业售后工单作为明确、可审核的应用切片；不要把招聘关键词改写成售后需求。取得获准样本前，只声称虚构样本的工程验证。若资料或试用对象长期不可得，按决策 0003 重新评估场景。
- **技术：** 保留 Python/Pydantic、当前 LangChain 模型调用和可替换的模型边界。产品内的 LangGraph、RAG、工具调用、数据库分别以实际状态恢复、资料遗漏、只读查找、保存审核记录等具体问题为进入条件。应用闭环完成后，可另做固定虚构样本的 RAG/只读工具对照实验，展示相关岗位能力，但不把实验写成售后需求。
- **交付顺序：** 先补可复现评估与最小 `ya` 入口；随后尽快做 FastAPI + 浏览器审核面板，展示应用岗看重的输入、依据、人工确认和失败处理。CLI 只需覆盖同一核心流程，交互式终端体验不占用主要验证时间。Electron 保留为用户确认的产品形态，在浏览器流程和桌面交付需求成立后实施。
- **作品说明：** 展示输入、资料版本、输出、人工复核与改动前后结果；分别写明本地虚构样本、获准试用和生产运行的证据层级。不能把一个单元测试、一次模型成功或框架依赖称为“生产级 Agent”。
