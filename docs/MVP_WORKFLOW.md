# MVP 工作流：制造业售后工单处理 Agent

> 状态：当前选定的 MVP 假设 v0.2。用户选择该方向作为起点；售后团队痛点、工单频率和产品价值仍需通过获准使用的真实或脱敏样本验证。

## 目标用户与任务

- **目标用户假设：** 制造业企业的售后支持、技术服务人员，以及审核复杂工单的资深工程师或服务主管。
- **触发事件：** 客户提交产品故障、安装、使用或保修相关服务请求。
- **待完成任务：** 阅读工单，结合指定的产品资料查找依据，整理问题、待补信息和建议下一步，准备一份可审核的客户回复草稿。
- **失败代价：** 错误维修建议可能影响设备或人身安全；错误保修判断或承诺会带来成本和客户信任风险。因此 Agent 只提供有依据的辅助建议，关键决定由人审核。

## MVP 流程

1. 售后人员粘贴或选择一条工单，并补充产品型号、故障场景等已知信息。
2. 用户选择或提供本次任务可用的产品手册、维修 SOP、保修政策或历史案例；首版不自动扫描整个企业知识库。
3. Agent 提取问题描述、产品信息和缺失字段；信息不足时生成待补问题，不猜测填空。
4. Agent 在允许使用的资料中查找依据，生成：
   - 工单摘要、产品型号和问题类别；
   - 有来源依据的发现；
   - 建议下一步与待客户补充的信息；
   - 回复草稿；
   - 需要人工升级的标记及原因。
5. 售后人员检查证据、修改建议并审核回复，然后复制或导出。
6. 解析或生成失败时保留输入和已有结果，显示失败环节并允许重试或手动处理。

## 证据与安全规则

- 产品规格、维修步骤、保修口径等事实必须链接到用户提供的资料出处；无法找到依据时明确标为未知或待确认。
- 区分资料原文、Agent 归纳和推断，不把推断写成企业政策或已确认诊断。
- 不能编造型号、故障原因、配件库存、保修状态、维修时长或客户承诺。
- 涉及人身/设备安全、危险操作、保修例外、资料冲突或证据不足时，说明原因并建议转交人工；不提供无依据的操作指令。
- 回复草稿必须基于工单和批准资料，未经售后人员确认不得发送。

## 首版范围

### 包含

- 手动输入一条工单文本和必要产品上下文。
- 用户明确选择少量产品文档或历史案例作为依据。
- 输出分类、摘要、证据、待补信息、建议下一步、升级标记和回复草稿。
- 售后人员审核后复制或导出。
- 显示所用资料、证据位置、未知项和失败状态。

### 暂不包含

- 自动接收邮件/客服平台/CRM 工单，或批量处理工单。
- 自动发送客户回复、更新工单状态或更改保修记录。
- 自动下发维修指令、远程控制设备或判断安全许可。
- 自动访问整个企业知识库、ERP、库存、客户账户或设备遥测。
- 预测故障根因、配件需求或维修成本的确定性结论。
- 多 Agent 编排、定时任务和无人值守执行。

若样本验证显示某项排除能力是完成首条工作流的必要条件，再另行记录依据和决策。

### 界面载体与入口

首版界面以**审核面板**为主，而不是聊天窗口：工单与资料、结构化结果、逐条证据、待确认项和可编辑草稿应能同屏对照。原因是聊天流容易把证据和待确认项挤散，用户可能直接复制草稿发给客户，与本文的证据与安全规则冲突。

载体按[决策 0004](decisions/0004-cli-and-desktop-entry-architecture.md) 分阶段推进：先用 `ya` CLI 跑通并核对结果，再用浏览器页面验证交互（FastAPI 本地服务），最后才做桌面壳。**界面载体的推进不扩大功能范围**；无论哪个阶段，发送、写入工单系统或修改保修记录的动作在界面上只提供复制/导出，仍需人工在外部完成。

## 首轮验证与验收

### 验证样本

先收集 5–10 条获准使用或脱敏的工单，并配套可引用的手册、政策或案例。记录人工处理基线，再比较 Agent 辅助后的结果。小样本用于发现问题，不用于宣称普遍效果。

在获得这些资料之前，使用 `examples/x100_case.md` 等完全虚构的样本验证工程边界。虚构样本通过不能证明售后团队有需求，也不能替代人工审核和业务效果评估。

### 当前虚构 E18 样本的评估卡

以下是对 `examples/x100_case.md` 的预期行为，用来检查后续重构和模型调用；它不是已经全部通过的测试报告。

- **必须保留输入边界：** 把“运行中显示 E18，随后停机”标为客户报告；把“E18 表示传感器信号异常，出现时停止运行并联系授权服务人员”标为指定手册内容。具体故障原因和停机机制仍为未知。
- **必须给出可审核结果：** 手册事实的引文逐字出现在本次指定资料中；结论、未知项、待补问题、升级原因和未发送的回复草稿可供售后人员核对。手册要求联系授权服务人员，因此应建议人工评估具体原因。
- **不得越过依据：** 不编造维修、断电或拆卸步骤、保修判断、处理时限、尚未执行的转交或人员安排；不把手册未要求的紧急程度写成确定要求。引文出现于资料中只是最低检查，仍要人工判断结论和草稿是否真的受其支持。
- **失败时保持可恢复：** 结构化解析为空或引文不在指定资料中时，标出失败环节，不把该草稿当成可发送结果；保留原始输入和可用诊断信息，允许人工处理。当前示例仅有错误提示，完整恢复能力仍待实现。

### 每条工单记录

- 人工首轮分析/起草耗时与 Agent 辅助后的总耗时；
- 分类、依据和建议被用户修改的部分及原因；
- 无依据陈述、错误政策引用、遗漏、误升级或未升级等错误；
- 结构化解析、引文核对和模型调用的失败环节、发生次数及人工处理方式；有可用计量数据时记录请求时延与模型用量/成本；
- 用户能否快速核对关键依据；
- 售后人员是否愿意在下一条类似工单继续使用。

### MVP 验收条件

- 用户能输入单条工单并提供必要产品背景和资料，获得上述结构化输出。
- 事实性产品/服务结论可追到资料出处；缺失信息清楚标示，不编造。
- 安全风险、政策冲突或证据不足会明确升级给人工。
- 用户可修改和导出回复草稿，系统不会未经确认发送或写入外部系统。
- 失败后原始输入与已有结果仍可恢复。
- 试用结果显示人工审核后有可观察的时间节省或处理质量改善；否则调整或暂停该场景，不直接扩展集成。
